# StarPony Insights

Внутренняя система аналитики для производственной компании StarPony. Показывает,
что продаётся, из чего это сделано, сколько материалов осталось и что пора закупать —
на данных учёта МойСклад.

Десять разделов: главная со сводкой, товары и материалы в отгрузках, материалы
в приёмках, поставщики, расчёт производства, инвентаризация, сроки оплаты,
прибыльность и каналы продаж.

**Статус: фаза 2, страницы разделов.** Приложение развёрнуто
на `insight.star-pony.ru`, данные синхронизируются по расписанию.
Готовы три страницы из десяти: товары и материалы в отгрузках, материалы
в приёмках. Что дальше — `docs/ROADMAP.md`, где мы сейчас — `docs/STATUS.md`.

## Стек

| Слой | Решение |
|---|---|
| Бэкенд | Python 3.12, Django 5.2 LTS, DRF, PostgreSQL 18 |
| Сервер приложения | gunicorn |
| Фронтенд | React 19, TypeScript, Vite, Tailwind, shadcn/ui |
| Данные на фронте | TanStack Query, TanStack Table, nuqs |
| Контракт API | drf-spectacular → openapi-typescript |
| Инфраструктура | Docker, Caddy, деплой через GitHub Actions |

Монорепозиторий: один push — одна версия системы, контракт API и фронтенд
не разъезжаются.

---

## Как это устроено

```
браузер → Caddy ─┬→ статика фронтенда
                 └→ gunicorn → Django
                        ↓
                    Postgres
```

Три контейнера, наружу смотрит только Caddy.

**Источник правды — Postgres, а не МойСклад.** В учётную систему ходят только
синхронизации по расписанию и обратная запись; ни один HTTP-запрос пользователя
не идёт в чужой API. Лимит запросов к МойСкладу общий с другими системами компании,
поэтому клиент читает заголовки остатка лимита и притормаживает заранее.

## Структура

```
backend/
├── config/        settings, urls, wsgi
├── core/models/   модели домена — одно место
├── moysklad/      клиент, синхронизации, обратная запись
├── api/           по разделам: urls, serializers, views, services
└── tests/

frontend/src/
├── app/           оболочка: роутер, провайдеры, раскладка
├── sections/      одна папка = один пункт меню
├── shared/        то, что понадобилось второму разделу
└── styles/
```

Фронтенд делится по разделам, а не по типам файлов: правка одной страницы
не должна требовать четырёх папок в разных концах дерева.

## Запуск

Всё целиком, включая базу:

```bash
docker compose -f docker-compose.local.yml up --build
```

Фронтенд — `localhost:3002`, API — `localhost:8002`, база — `localhost:5433`.
Миграции применяются при старте, отдельная команда не нужна.

Можно и без контейнеров — тогда база всё равно берётся из compose:

```bash
docker compose -f docker-compose.local.yml up -d db

cd backend && python manage.py runserver 127.0.0.1:8002
cd frontend && npm run dev
```

Типы фронтенда генерируются из схемы Django, а не пишутся руками:

```bash
cd frontend && npm run api:types
```

Перед коммитом хуки сами гоняют сканер секретов, линтеры, проверку типов
и тесты бэкенда. Ставятся один раз: `pre-commit install`.

Проверки целиком:

```bash
cd backend && pytest                    # 513 тестов
cd frontend && npm run typecheck && npm run lint && npm test   # 104 теста
```

**Проверять надо там, где код исполняется.** `shadcn` CLI ставит зависимости
в `node_modules` хоста, а dev-сервер живёт в контейнере со своим томом:
зелёная сборка на хосте ничего не говорит о странице в браузере.

```bash
docker exec starpony-local-frontend npm run build
```
