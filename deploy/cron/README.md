# Синхронизация по расписанию

## Как устроено

Cron вызывает `starpony-sync.sh`, тот запускает management-команду внутри
контейнера. Celery и Redis не используются намеренно: они заняли бы
100–150 МБ там, где считается каждый мегабайт, ради задачи, которую решает
строка в crontab.

Защита от наложения двойная: `flock` не даёт запуститься второму процессу,
а advisory-блокировка Postgres — второму прогону внутри базы. Первая экономит
память, вторая защищает данные; ни одна не заменяет другую.

## Установка

```bash
# Едут сами при деплое бэкенда. Вручную:
scp -r deploy root@<сервер>:/root/starpony/
ssh root@<сервер> 'chmod +x /root/starpony/deploy/cron/starpony-sync.sh'

# Добавить строки в crontab, не затирая существующие
ssh root@<сервер> 'crontab -l > /tmp/cron.bak && \
  cat /root/starpony/cron/starpony.cron >> /tmp/cron.bak && \
  crontab /tmp/cron.bak && crontab -l | grep starpony'
```

## Проверка живости — не подключена, и это осознанно

Внешний наблюдатель не заводится: несостоявшаяся синхронизация — это
устаревшие данные, а не потеря. Полный проход восстанавливает всё за
20 секунд, а о сбое скажет отметка «данные на 14:32» в шапке страницы.

Точка подключения оставлена на случай, если понадобится: вписать адреса
в `HEALTHCHECK_DOCUMENTS` и `HEALTHCHECK_STATE` в crontab, править код
не нужно. Пустые переменные — скрипт молчит.

Тогда он шлёт три сигнала: `/start` перед запуском, пустой при успехе
и `/<код>` при ошибке — видно не только «не пришло», но и «пришло с ошибкой»,
и «идёт слишком долго».

## Журнал

`/var/log/starpony_sync.log`, по строке на прогон с отметкой времени.

Ротация настраивается один раз:

```bash
ssh root@<сервер> 'cp /root/starpony/deploy/cron/starpony-logrotate /etc/logrotate.d/starpony'
```

Без неё файл растёт на несколько сотен мегабайт в год: только обновление
остатков даёт около 35 тысяч строк.
